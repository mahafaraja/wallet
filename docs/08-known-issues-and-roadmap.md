# 08 · Known issues and roadmap

[← Documentation index](README.md)

This is an **as-implemented assessment**, not a list of completed features. It was prepared by tracing the current source and, for the backup validation issue, reproducing the failure with a representative exported preference record. Priorities indicate potential user impact, not a promise of delivery order.

> Until the critical items are fixed and tested, treat Pocket Ledger as a prototype. Do not make it the only source of important financial data. Keep the existing browser data and any exported JSON files.

## Critical: data recovery and financial accuracy

| Area | Current behavior / risk | Source | Recommended next step |
| --- | --- | --- | --- |
| **JSON restore** | The validator requires `id` for every table row, but `preferences` and `syncMetadata` use `key`. A normal exported file with preference records can be rejected. | `src/data/sync/backupCodec.ts` → `parseBackup` | Validate primary keys per store; add real export→import round-trip tests for all nine stores. |
| **Merge / replace** | `mergeRecords` assumes ID/revision on keyed preference stores; `replaceAll` uses `bulkPut` without clearing tables. UI wording does not guarantee the behavior implied by “replace” or “nothing discarded.” | `src/data/sync/adapter.ts`, `syncManager.ts`, `src/data/repository.ts` | Define exact merge vs replace semantics; validate all rows/references; use transactional writes; test collisions, keyed tables, rollback and recovery. |
| **Cross-currency transfers** | The form allows destination accounts in a different currency. `accountBalance()` applies the same raw `amountMinor` to both accounts without conversion. | `TransactionSheet.tsx`, `src/lib/finance.ts` | Either restrict transfers to equal currencies or store separate source/destination amounts and an explicit rate with safe rounding; test edits/deletes. |
| **Mixed-currency aggregates** | Goal overview, Activity day totals, suggested spending and budget performance can sum or compare amounts without converting/grouping all currencies correctly. | `GoalsScreen.tsx`, `ActivityScreen.tsx`, `BudgetsScreen.tsx`, `finance.ts` | Audit every aggregate; group by currency or use a user-authorized conversion; add mixed-currency regression tests and visible exclusions. |
| **Demo reset** | `clearDemoData()` deletes category IDs beginning with `cat_`, including custom IDs generated by the app, then recreates built-ins. It can also remove sample accounts while user records still reference them. | `src/data/seed.ts`, `SettingsScreen.tsx` | Isolate demo data explicitly, prevent or repair dangling references, and prove that resetting samples preserves all user-created records. |

## High: privacy, reliability and correctness

| Area | Current behavior / risk | Source | Recommended next step |
| --- | --- | --- | --- |
| **Hide amounts** | `Money` values are masked, but directly formatted amounts and charts can remain visible. It is not encryption. | `src/components/Money.tsx`, multiple screens | Route all sensitive render paths through a common privacy-aware formatter; test every screen and tooltip. |
| **Goal withdrawals** | No check prevents withdrawing more than the goal's saved total. Linked deposits/withdrawals are modeled as expense/income, so they affect reports. | `GoalsScreen.tsx`, `repository.ts` → `contributeToGoal` | Validate balances inside one IndexedDB transaction, define goal/account accounting semantics and test concurrent operations. |
| **Offline coverage** | The shell is pre-cached, but not all hashed assets or lazy screen chunks are pre-cached. A missing asset can receive an HTML fallback. | `public/sw.js`, `src/pwa/registerSW.ts` | Precache a versioned build manifest and test a fresh offline reload, lazy routes, updates and iOS behavior. |
| **Currency rates** | A non-reporting transaction uses a manually entered rate, but Settings receives `rates={{}}` and a no-op change handler from `App.tsx`. General rate fields do not persist or feed transaction entry. | `src/App.tsx`, `SettingsScreen.tsx`, `TransactionSheet.tsx` | Wire the stored-rate hook, define when rates are applied, preserve original amounts and test reporting-currency changes. |
| **Revision / conflicts** | Revisions are based on local wall clocks; no deletion tombstones or complete per-table conflict rules exist. This is not reliable multi-device synchronization. | `repository.ts`, `adapter.ts`, `syncManager.ts` | Design version vectors or another explicit protocol, tombstones, conflict UI, validation and recovery before enabling cloud sync. |
| **Local storage** | Browser data is unencrypted and can be cleared, evicted, unavailable or separated by origin/profile. The app has no reliable remote backup yet. | `src/db/database.ts`, browser platform | Implement reliable local export/import; document storage risks; test quota/private-mode failures and request persistence where appropriate. |
| **Money input / rounding** | Excess precision is truncated. Conversions use JavaScript numbers and require more boundary testing; the currency catalog needs authoritative verification for each currency. | `money.ts`, `currency.ts`, `validate.ts` | Define validation and rounding rules, reject or explicitly confirm excess precision, verify catalog, test overflow and negative/boundary conversions. |
| **Historical budgets** | Editing an existing budget changes the same stored cap, including for months from its start. It does not keep per-month versions. | `repository.ts` → `setBudget`, `finance.ts` | Introduce effective-dated or per-month budget records and migrate existing data safely. |

## Product gaps and architectural debt

| Area | Current state | Recommended next step |
| --- | --- | --- |
| **Account / goal editing** | Edit/delete helpers and sheets exist, but list/detail screens currently only open new-account/new-goal sheets. | Add explicit, tested edit actions and confirmation flows. |
| **Custom categories** | Repository helpers exist, but there is no working category-management screen wired into `App.tsx`. | Build the UI, routing, safeguards and tests. |
| **Recurring items** | Demo schedules and data helpers exist; there is no complete editor or automatic posting. | Implement schedule management and decide whether posting is manual or scheduled. |
| **App shortcut** | Manifest includes an `?action=add` shortcut, while the router reads the URL hash and the app does not currently act on that query parameter. | Wire and test shortcut behavior, or remove the unsupported shortcut. |
| **Demo labeling** | Demo IDs are identifiable in storage, but individual rows are not consistently labeled as sample data. Startup considers accounts and transactions when deciding whether data exists, not every table. | Provide a clear demo mode and explicit exit, with complete initialization checks. |
| **Dexie boundary** | The repository is not the only database access point: app composition, preference hooks, quick-add, seed and backup codec also use `db`. | Consolidate reads/writes behind a documented interface; preserve reactive updates. |
| **Index use / scale** | Some list operations load whole tables and filter in memory despite available indexes. | Query indexed ranges where useful; measure performance with large datasets. |
| **Testing** | Unit tests cover useful money/finance and navigation cases, not comprehensive IndexedDB, backup, offline, accessibility or real-device flows. | Add database integration, browser end-to-end, import round-trip, cross-currency and migration tests. |
| **Authentication / Drive** | No login or cloud sync is implemented. The Google Drive adapter deliberately reports not connected. | Design authentication separately from Drive authorization; implement least-privilege access only after backup integrity is established. |

## Suggested order of work

1. **Protect existing data:** repair and test JSON export/import, merge/replace and demo reset before advising users to move or clear data.
2. **Protect financial calculations:** block or correctly model cross-currency transfers; fix mixed-currency aggregates, goal withdrawal limits, rounding and precision validation.
3. **Make the current product coherent:** finish account/goal editing, custom categories, recurring management, privacy masking and settings rates.
4. **Prove offline and migration behavior:** automated browser tests, schema upgrades, cache versioning, failure/recovery paths and device testing.
5. **Add identity and cloud sync later:** separately designed authentication and Drive authorization, user-visible backup files, deletion handling and conflict resolution.

For each fix, add tests that reproduce the previous failure and verify that existing user records are preserved. Update the corresponding documentation when behavior changes.
